# 상품 이미지 업로드 설계

> 구현 상태: 2026-08-06 기준 DB migration, Storage bucket, 이미지 교체 API, 등록·수정 화면, 목록 썸네일 및 상세 대표 이미지까지 구현 완료. 로컬 migration 적용과 프런트엔드 production build를 검증했다.

## 1. 현재 문제

상품 편집기는 이미지를 선택하고 1024×1024 WebP로 자르지만, 결과를 브라우저의 `File[]`과 `blob:` 미리보기 URL에만 보관한다. 상품 등록·수정 요청에는 상품 정보 JSON만 포함되며, 서버에는 상품 이미지용 테이블·Storage bucket·업로드 API가 없다.

따라서 현재 이미지는 서버에 전송되거나 상품과 연결되지 않으며 페이지를 벗어나면 사라진다.

## 2. 목표와 정책

- 상품마다 이미지 1~5장을 순서대로 저장한다.
- 첫 번째 이미지를 대표 이미지로 사용한다.
- 클라이언트는 1024×1024 WebP로 변환하고, 서버도 파일 형식과 크기를 다시 검증한다.
- 변환 후 파일은 장당 최대 2MB로 제한한다.
- 상품 생성·수정 권한과 이미지 변경 권한을 동일하게 적용한다.
- 이미지 변경 실패 시 상품 정보와 이미지 목록이 서로 어긋나지 않아야 한다.
- 상품 휴지통 이동 중에는 이미지를 유지하고, 실제 영구 삭제 시 Storage 객체도 제거한다.

## 3. 데이터 모델

별도 테이블을 사용한다. `market_items`에 URL 배열을 직접 저장하면 이미지별 순서, 교체, 삭제 및 정합성 관리가 어렵다.

```sql
create table public.market_item_images (
  id bigint generated by default as identity primary key,
  item_id bigint not null references public.market_items(id) on delete cascade,
  storage_path text not null unique,
  position smallint not null,
  created_at timestamptz not null default now(),
  constraint market_item_images_position check (position between 0 and 4),
  constraint market_item_images_item_position unique (item_id, position)
);

create index market_item_images_item_idx
  on public.market_item_images (item_id, position);
```

Storage bucket:

- bucket: `market-item-images`
- public: `true` (현재 상품과 블로그 프로필 이미지가 공개 URL을 사용하는 구조와 일치)
- MIME: `image/webp`
- 파일 크기 제한: 2MB
- 객체 경로: `{sellerId}/{itemId}/{uuid}.webp`

DB에는 공개 URL이 아니라 `storage_path`만 저장한다. API 응답 시 환경별 Supabase URL과 bucket 이름으로 URL을 조립한다.

## 4. API 계약

상품 생성과 이미지 업로드를 분리한다. Edge Function에서 큰 multipart 요청과 상품 JSON 생성을 한 번에 처리하는 것보다 재시도와 오류 복구가 단순하다.

### 상품 생성

`POST /market/items`

기존 상품 JSON을 저장하고 생성된 `item.id`를 반환한다. 신규 등록 화면에서는 이미지가 최소 한 장 선택되지 않으면 이 요청을 보내지 않는다.

### 이미지 일괄 교체

`PUT /market/items/{id}/images`

요청은 `multipart/form-data`이며 동일한 `images` 필드로 1~5개 파일을 순서대로 전송한다.

성공 응답:

```json
{
  "data": [
    { "id": 1, "url": "https://.../0f...webp", "position": 0 },
    { "id": 2, "url": "https://.../91...webp", "position": 1 }
  ]
}
```

검증:

- 로그인 및 CSRF 토큰
- 상품 소유자 일치
- 판매 완료 또는 삭제된 상품은 수정 불가
- 1~5개 파일
- 각 파일의 선언 MIME과 실제 WebP 시그니처 확인
- 각 파일 2MB 이하

### 조회 응답

모든 `MarketItem` 응답에 아래 필드를 추가한다.

```json
{
  "images": [
    { "id": 1, "url": "https://...", "position": 0 }
  ],
  "thumbnailUrl": "https://..."
}
```

목록 API는 `thumbnailUrl`만 필요하므로 목록 쿼리에서는 대표 이미지 한 장만 조회하고, 상세 API에서는 `images` 전체를 조회한다. 초기 구현에서는 일괄 조회 후 `item_id`로 묶어 N+1 쿼리를 피한다.

## 5. 저장 흐름

### 신규 상품

1. 클라이언트에서 이미지 선택, 크롭, WebP 변환을 완료한다.
2. 이미지가 없으면 상품 등록 버튼 옆에 검증 오류를 표시한다.
3. `POST /market/items`로 상품을 생성한다.
4. 반환된 ID로 `PUT /market/items/{id}/images`를 호출한다.
5. 모두 성공하면 상품 상세로 이동한다.
6. 이미지 업로드가 실패하면 생성된 상품은 유지하되 편집 화면에 머물고, "상품 정보는 저장됐지만 이미지 업로드에 실패했습니다"와 재시도 버튼을 보여준다. 클라이언트는 생성된 ID를 상태에 보관해 상품 중복 생성을 막는다.

### 상품 수정

1. 기존 이미지 URL을 `persistedImages`, 새 파일을 `newFiles`로 구분해 표시한다.
2. 상품 JSON 변경은 `PATCH /market/items/{id}`로 저장한다.
3. 이미지 목록이 변경된 경우에만 `PUT /market/items/{id}/images`로 최종 1~5장을 일괄 교체한다.
4. 업로드 실패 시 기존 서버 이미지 목록은 그대로 유지되고 사용자는 재시도할 수 있다.

## 6. 서버의 일괄 교체 알고리즘

1. 요청과 소유권을 검증한다.
2. 모든 파일을 새 UUID 경로로 Storage에 업로드한다.
3. 하나라도 실패하면 이번 요청에서 업로드한 새 객체를 모두 제거하고 기존 DB 행은 건드리지 않는다.
4. 모든 업로드가 성공하면 DB 트랜잭션용 RPC에서 기존 이미지 행을 새 행으로 교체한다.
5. DB 교체가 실패하면 새 객체를 제거한다.
6. DB 교체가 성공하면 이전 Storage 객체를 제거한다.

Storage와 Postgres를 단일 트랜잭션으로 묶을 수 없으므로 이 보상 작업이 필요하다. 이전 객체 삭제 실패는 응답을 실패시키지 않고 로그를 남긴 뒤 정리 작업 대상으로 처리한다. DB가 새 경로를 가리키는 시점부터 사용자 데이터는 정상이다.

## 7. 삭제 수명 주기

- 휴지통 이동: 이미지 행과 객체 유지. 복원 시 즉시 다시 노출할 수 있다.
- 대화가 없는 상품의 영구 삭제: `ON DELETE CASCADE`로 이미지 행 삭제 후, 삭제 전 읽어 둔 Storage 경로들을 제거한다.
- 대화가 있어 tombstone으로 남는 상품: 이미지 행과 Storage 객체를 제거하여 삭제된 상품 이미지가 계속 공개되지 않게 한다.
- 주기 정리 작업: DB에서 참조되지 않고 일정 시간 이상 지난 `market-item-images` 객체를 제거한다.

## 8. 클라이언트 변경

- `MarketItem`에 `images`와 `thumbnailUrl` 추가.
- `MarketEditor`의 로컬 `imageFiles`만 사용하는 상태를 다음으로 변경:
  - `persistedImages`: 서버에 저장된 이미지
  - `draftImages`: 기존 이미지 또는 새 `File`을 순서대로 담은 편집 목록
  - `createdItemId`: 신규 상품 생성 후 이미지 재시도에 사용할 ID
- 등록 중 단계 문구를 `상품 정보 저장 중` → `이미지 업로드 중 (n/전체)`로 표시.
- 상세 화면의 placeholder를 실제 `images` 갤러리로 교체.
- 마켓 목록, 블로그 상점, 관리 목록에 `thumbnailUrl` 사용.
- `URL.createObjectURL`은 각 파일당 한 번만 만들고 제거·unmount 시 revoke한다.

## 10. 완료 조건

- 상품 등록 후 새로고침해도 이미지가 남는다.
- 다른 사용자는 이미지 교체가 불가능하다.
- 5장 순서와 대표 이미지가 모든 화면에서 동일하다.
- 이미지 업로드 중 실패해도 기존 이미지가 유실되지 않는다.
- 상품 영구 삭제 후 DB 행과 Storage 객체가 함께 정리된다.
- 상품 목록 조회가 이미지 수만큼 추가 쿼리를 발생시키지 않는다.
